## 1. Sistema de Roles

Se implementó un sistema de tres roles con permisos diferenciados: **ADMIN**, **SUPERVISOR** y **RECEPCIONISTA**.

La regla principal es que si un usuario tiene `is_superuser=True` en la base de datos, automáticamente se le asigna el rol **ADMIN** y el estado **ACTIVE**, sin importar qué otros valores tenga. Esto se garantiza en dos capas:

- En el método `save()` del modelo (cada vez que se guarda un usuario).
- En el `LoginSerializer` (cada vez que se loguea).

Cada rol ve un menú distinto en el sidebar:

| Rol | Links visibles |
|---|---|
| **ADMIN** | Inicio · Dashboard · Estadísticas · Habitaciones · Check-in/out |
| **SUPERVISOR** | Inicio · Estadísticas |
| **RECEPCIONISTA** | Inicio · Habitaciones · Check-in/out |

El badge del rol también cambia de color: verde para Administrador, azul para Supervisor y amarillo para Recepcionista.

## 2. Modelo de Usuario ampliado

El modelo `User` ahora hereda de `AbstractUser` con estos campos nuevos:

| Campo | Tipo | Notas |
|---|---|---|
| `role` | `CharField(choices)` | `ADMIN`, `SUPERVISOR`, `RECEPCIONISTA` (default `RECEPCIONISTA`) |
| `status` | `CharField(choices)` | `PENDING`, `ACTIVE`, `BLOCKED` (default `PENDING`) |
| `telefono` | `CharField` | Opcional |
| `dni` | `CharField` | Único |
| `domicilio` | `CharField` | Opcional |
| `fecha_nacimiento` | `DateField` | Opcional |

Además tiene una propiedad calculada llamada **`edad`** que devuelve la edad del usuario automáticamente a partir de la `fecha_nacimiento`. No se guarda en la base de datos, se calcula al momento de consultarla.

El método `save()` fue sobrescrito para garantizar que cualquier superusuario quede con `role=ADMIN` y `status=ACTIVE` en cada guardado.

## 3. Autenticación con JWT enriquecido

El `LoginSerializer` fue extendido para incluir más información en el token JWT y en la respuesta del login:

- **En el JWT**: se agregan los claims `username`, `role`, `status` e `is_superuser`.
- **En el body de respuesta**: se devuelven los mismos campos para que el frontend los use sin decodificar el token.

El serializer también valida el estado del usuario al loguearse:

- **RECEPCIONISTA** o **SUPERVISOR** con estado **PENDING** → error con el mensaje *"Tu cuenta está pendiente de aprobación por un administrador."*
- Estado **BLOCKED** → error con *"Tu cuenta ha sido bloqueada. Contacta al administrador."*
- Los **superusers** siempre pasan, sin importar el estado.

Del lado del frontend, el archivo `auth.ts` tiene:

- `syncSessionFromToken()`: decodifica el JWT y guarda `role` e `is_superuser` en `localStorage`.
- `getSessionRole()`: devuelve el rol actual con soporte para los tres roles.
- `fetchMe()`: consulta `/auth/me/` para reforzar el rol desde la base de datos (fuente de verdad).

## 4. Endpoints nuevos en el backend

| Método | Endpoint | Permiso | Descripción |
|---|---|---|---|
| `POST` | `/api/v1/auth/register/` | Público | Registrar recepcionista (`PENDING` por default) |
| `GET` | `/api/v1/auth/receptionists/` | Solo Admin | Listar recepcionistas con `edad` calculada |
| `PATCH` | `/api/v1/auth/receptionists/:id/status/` | Solo Admin | Aprobar (`ACTIVE`) o bloquear (`BLOCKED`) |
| `POST` | `/api/v1/habitaciones/ocultar-piso/` | Auth | Ocultar/mostrar todas las habitaciones de un piso |

**Detalle de cada uno:**

- **`POST /api/v1/auth/register/`** — público, permite que un recepcionista se registre. Crea el usuario con `role=RECEPCIONISTA` y `status=PENDING`.
- **`GET /api/v1/auth/receptionists/`** — solo Admin. Devuelve la lista de todos los recepcionistas con sus datos de perfil, incluyendo el campo calculado `edad`.
- **`PATCH /api/v1/auth/receptionists/:id/status/`** — solo Admin. Permite aprobar (`ACTIVE`) o bloquear (`BLOCKED`) a un recepcionista.
- **`POST /api/v1/habitaciones/ocultar-piso/`** — recibe `{ piso, oculta }` y actualiza en bloque todas las habitaciones del piso indicado.

## 5. Dashboard diferenciado por rol

La ruta `/dashboard` ahora es contextual según el rol:

- **ADMIN** ve dos tabs: **"Aceptar Recepcionistas"** y **"Editar Hotel"**.
- **SUPERVISOR** ve únicamente la tab **"Editar Hotel"**.
- **RECEPCIONISTA** no accede al dashboard (redirige a `/`).

Se agregó también la ruta **`/admin/stats`** accesible para ADMIN y SUPERVISOR, que muestra un placeholder con tarjetas de estadísticas (Ocupación hoy, Check-ins del día, Check-outs del día, Ingresos del día). Es la base para el dashboard de análisis y queda lista para conectar datos reales en el futuro.

## 6. Control de creación (solo ADMIN)

Solo el rol de administrador puede crear habitaciones y pisos nuevos. Para el recepcionista:

- En `/rooms`, el botón **"Nueva habitación"** no se muestra.
- En la grilla, los tiles **"+ Nuevo"** de cada piso no aparecen.
- La creación de pisos y habitaciones quedó centralizada en `/dashboard → Editar Hotel`, que solo los admin ven.

El recepcionista sí puede seguir viendo la grilla, filtrar por estado, hacer check-in y check-out con normalidad.

## 7. Registro de recepcionistas (frontend)

Se implementó la pantalla completa de registro de recepcionistas en `/register`, accesible de forma pública (sin login previo).

### Acceso

- Ruta pública `/register`.
- Link **"¿No tenés cuenta? Registrate como recepcionista"** debajo del botón "Ingresar" en el login.

### Campos del formulario

| Campo | Requerido | Validación |
|---|---|---|
| Nombre | ✅ | No vacío |
| Apellido | ✅ | No vacío |
| Email | ✅ | Formato de email válido. Se usa como `username` para el login |
| Teléfono | ✅ | No vacío |
| DNI | ✅ | No vacío |
| Domicilio | ✅ | No vacío |
| Fecha de nacimiento | ✅ | Debe tener 18+ años |
| Contraseña | ✅ | Mínimo 6 caracteres |
| Repetir contraseña | ✅ | Debe coincidir con la anterior |

### Edad calculada automáticamente

Al elegir la fecha de nacimiento, el campo **"Edad"** se calcula en tiempo real (sin consultar al backend) y se muestra en el formulario. Se valida que sea mayor o igual a 18 años antes de permitir el registro.

### Flujo del registro

1. El usuario completa el formulario y hace click en **"Crear cuenta"**.
2. Se validan todos los campos del lado del cliente.
3. Se envía `POST /api/v1/auth/register/` con los datos.
4. El backend crea el usuario con `role=RECEPCIONISTA` y `status=PENDING`.
5. Se muestra una pantalla verde de confirmación: *"¡Cuenta creada! Tu cuenta está pendiente de aprobación. Un administrador debe activarla antes de que puedas iniciar sesión."*
6. Después de 2.5 segundos, redirige automáticamente a `/login`.

### Validaciones server-side

Si el DNI ya existe o el email ya está registrado, el backend devuelve un error que se muestra directamente en el formulario.

### Decisión de diseño

Como el backend requiere `username` y el PDF solo pide email, se usa el **email como username** (en minúsculas). Consecuencia: el recepcionista inicia sesión con su **email** en lugar de un nombre de usuario separado. Es un patrón común y evita agregar un campo extra al formulario.

## 8. Gestión de recepcionistas desde el admin

El panel del administrador ahora consume datos reales del backend en lugar de datos mock.

### Cambios técnicos

- **Nuevo archivo `api/receptionists.ts`** con:
  - `getReceptionists()`: hace `GET /auth/receptionists/` y mapea del backend al frontend.
  - `updateReceptionistStatus(id, action)`: hace `PATCH /auth/receptionists/:id/status/` con `action='accept'` o `action='block'`.

- **Mapeo de estados**:

  | Backend | Frontend |
  |---|---|
  | `PENDING` | `pendiente` |
  | `ACTIVE` | `aceptado` |
  | `BLOCKED` | `bloqueado` |

- **`ReceptionistCard.tsx`** ahora recibe el tipo `Receptionist` (con `id: number`) en lugar de `MockReceptionist`.

- **`DashboardPage.tsx`** carga datos reales:
  - `useEffect` dispara la carga al entrar al tab "Aceptar Recepcionistas".
  - Maneja estados `loading`, `error` y `items.length === 0`.
  - Después de aprobar o bloquear, refresca la lista automáticamente.
  - El contador de pendientes se actualiza en tiempo real.

### Comportamiento por estado del recepcionista

| Estado | Color de la tarjeta | Botones visibles |
|---|---|---|
| **Pendiente** | Blanco | ✓ Aprobar + 🚫 Bloquear |
| **Aceptado** | Verde | 🚫 Bloquear |
| **Bloqueado** | Gris con opacidad | ✓ Aprobar |

### Flujo desde el admin

1. Un recepcionista se registra → aparece en el dashboard como **"Pendiente"**.
2. El admin hace click en ✓ → el usuario pasa a `ACTIVE` en la base de datos.
3. El recepcionista ya puede iniciar sesión.
4. Si el admin hace click en 🚫 → el usuario pasa a `BLOCKED`.
5. En el siguiente login, el recepcionista ve un error: *"Tu cuenta ha sido bloqueada. Contacta al administrador."*
